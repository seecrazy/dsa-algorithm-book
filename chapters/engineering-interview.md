## 1. 面试不是考试，是协作调试

面试官想看到：

1. 能否澄清约束；
2. 能否提出暴力解并分析瓶颈；
3. 能否选择合适的结构；
4. 能否写出可运行边界；
5. 能否主动测试和修复。

推荐节奏：

```text
重复题面 -> 举例子 -> 暴力解 -> 瓶颈 -> 优化状态 -> 伪代码 -> 编码 -> 自测
```

## 2. 从暴力到优化

| 暴力形态 | 常见优化 |
|---|---|
| 两层循环找 pair | 哈希、排序 + 双指针 |
| 所有子数组 | 前缀和、滑动窗口 |
| 所有子集 | 状压 DP、位运算 |
| 所有排列 | 回溯剪枝 |
| 每次扫描最值 | 堆、单调栈/队列 |
| 判断连通 | DFS/BFS、并查集 |

## 3. 写代码前回答四问

1. 输入可能为空吗？
2. 有重复值吗？
3. 是否允许修改输入？
4. 答案不唯一时返回哪个？

这四问能避免大量边界 Bug。

## 4. 自测模板

写完后至少检查：

```text
空输入
单元素
两个相等元素
全部递增/递减
目标在开头/结尾/不存在
负数或零
最大规模
```

面试时不要默写测试名，要具体说值。

## 5. 工程化设计题

### Rate Limiter

可选算法：

- 固定窗口：简单，有边界突刺；
- 滑动日志：精确，内存大；
- 滑动窗口计数：折中；
- Token Bucket：允许短时突发。

需要讨论分布式锁、Redis TTL、时间同步和失败降级。

### LRU / LFU

- LRU：哈希 + 双向链表；
- LFU：频次桶 + 每个频次内 LRU；
- 工程中还要考虑容量、TTL、并发读写和缓存穿透。

LFU 的频次桶结构值得多说一句：外层按频次递增维护一串桶，每个桶内是该频次的双向链表；命中时把节点从频次 f 的桶摘下、头插进 f+1 的桶，容量满时从最小频次桶的尾部淘汰。get/put 都能 O(1)，代价是新增频次要建桶、空桶要回收；工程里也常用堆或近似计数（如 Top K 一节的 Count-Min Sketch）替代精确 LFU。

### Top K 流式统计

- Count-Min Sketch 估计频次；
- 小根堆维护 K；
- 分片统计后聚合；
- 时间窗口滚动重置。

### 数据一致性

- 数据库索引：B+ tree 支持范围；
- 缓存：旁路缓存、失效策略；
- 消息：幂等键、去重表；
- 校验：哈希校验和、版本号。

## 6. Debug 纪律

遇到错误不要乱改：

1. 复现最小输入；
2. 打印关键不变量；
3. 二分定位失败步骤；
4. 解释为什么修复后正确；
5. 再补一个针对该 Bug 的测试。

## 7. 沟通句式

```text
我先假设输入规模是 ______；
暴力做法是 ______，复杂度 ______；
瓶颈在 ______；
我可以把 ______ 变成键/状态/有序边界；
这样把 ______ 降到 ______；
边界包括 ______。
```

> 专业不是没有 Bug，而是有办法快速把错误变成可解释、可修复、可预防的事实。
